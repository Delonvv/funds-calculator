# Автоматические проверки funds-calculator

Workflow `.github/workflows/project-checks.yml` работает независимо от
`.github/workflows/update-funds.yml`. Существующее обновление, его расписание,
финансовые показатели и настройки Netlify не изменяются.

## Расписание и запуск

- Ежедневно в 04:17 UTC — 09:17 по Екатеринбургу: статический сайт,
  JavaScript, JSON, сценарная арифметика и основные функции в Chromium.
- Каждый понедельник в 04:47 UTC — 09:47 по Екатеринбургу: те же проверки,
  плюс свежесть данных и результаты обновляющего workflow.
- На pull request — ежедневный набор без записи в Issues.
- Через Run workflow — ежедневный набор; флаг `weekly` добавляет недельный.
  Запуск из ветки, отличной от `main`, не создаёт и не изменяет Issues.

GitHub выполняет расписания после попадания workflow в основную ветку и может
задерживать запуск. Подготовка PR не активирует расписания. Отдельного cron
на сервере или автоматизации Codex не требуется.

## Что проверяется

У сайта нет обязательной сборки. Вместо фиктивного build проверяются HTML-точка
входа, наличие локальных ресурсов, синтаксис встроенных и отдельных скриптов,
разбор JSON и основные ограничения их структуры.

Числовые примеры вызывают существующие функции калькулятора фондов из
`index.html`: убыток, нулевой взнос, дни/месяцы, комиссия, налоговый порог
и отключение налога по вкладу. Браузерные примеры проверяют Т‑Счёт,
Инвестзайм, ежемесячные выплаты, капитализацию вклада, СПК и НСЖ.
Сравнение выполняется с независимыми числовыми эталонами и начислением по периодам.
Это тесты действующей сценарной модели, а не подтверждение налоговых правил,
инвестиционного прогноза или актуальности ставок по первоисточникам.

Браузер проверяет поиск, доступность по квалификации, сброс, сравнение,
избранное фондов и продуктов после перезагрузки, передачу срока и ставки
из подборки, калькулятор и Escape, навигацию и переполнение на ширинах
360, 390, 768 и 1440 px, резервный каталог при недоступном `funds.json`.
Внешние запросы страницы блокируются для воспроизводимости. Сам сайт
не публикуется; production и внешние API котировок этим тестом не проверяются.

Недельный набор проверяет `updatedAt` у `funds.json`, `market-rates.json`,
`dcm.json`, `lastRun` и `failedTickers`, даты отдельных котировок, истории,
СЧА и значения RUSFAR. По GitHub API читаются последние 100 запусков
`update-funds.yml` для `main`: последний завершённый должен быть успешным
и не старше 36 часов; сбои и отмены за последние 7 дней попадают в отчёт,
даже если более поздний запуск восстановился.

Допуски мониторинга заданы в `weekly.mjs`: 3 календарных дня для файлов и
попытки обновления; 7 дней для котировок, истории MOEX и значения RUSFAR;
90 дней для ручной истории и СЧА. Семидневный запас допускает обычные выходные,
но не заменяет полноценный биржевой календарь: длительные праздники и
приостановка торгов требуют оценки отчёта человеком. СЧА без даты считается
непроверяемой и отмечается ошибкой. СЧА и ручная история действующим workflow
не обновляются — недельный мониторинг лишь сообщает о просрочке.

Наличие котировок проверяется, но для внебиржевых инструментов не требуется
обязательная котировка каждого тикера. Мониторинг не подтверждает цену по
живому первоисточнику, не анализирует логи обновлятора и не доказывает итоговую
публикацию Netlify. Для полного отказа API с ошибочно успешным статусом
обновлятора используются отдельные даты значений и `failedTickers`.

## Отчёты без повторяющихся Issues

Каждый запуск сохраняет артефакт `project-check-results` на 14 дней:
`report.json`, `summary.md`, снимки неуспешных браузерных сценариев.
Сводка также находится на странице запуска Actions.

Только расписание или ручной запуск из `main` может писать Issues.
Отдельная задача имеет `issues: write`; задача тестирования получает лишь
`contents: read` и `actions: read`. Секреты Netlify не используются.
Для предотвращения одновременного создания Issues мониторинговые запуски
выполняются последовательно через собственную concurrency-группу.

Используются две Issue с постоянными скрытыми маркерами: `daily` и `weekly`.
Поиск охватывает открытые и закрытые обращения GitHub Actions bot во всех
страницах API. Повторный сбой обновляет тело существующей Issue без новых
комментариев; восстановление закрывает её; возврат проблемы переоткрывает.
Здоровая недельная группа оценивается только при недельном запуске.
Чужие обращения не изменяются. Не удаляйте скрытый маркер из управляемой Issue.

При сбое установки, самотестов или отсутствии артефакта reporter создаёт
сообщение об ошибке инфраструктуры вместо ложного успеха. Если GitHub запрещает
создание Issues из Actions или API недоступен, задача report завершится ошибкой;
журналы и артефакты останутся доступными. Issues должны быть включены в репозитории.

## Локальная проверка

```sh
npm ci --prefix checks --ignore-scripts
cd checks
npx playwright install chromium
npm test
npm run daily
```

Для недельного прогона из корня:

```sh
GITHUB_REPOSITORY=Delonvv/funds-calculator GITHUB_TOKEN=<read-only-token> node checks/run.mjs --weekly
```

Передавайте токен через окружение или менеджер секретов; не сохраняйте его в файлы
или историю команд. Недельный прогон только читает GitHub API, не создаёт Issues.
Локально можно выбрать установленный Chromium переменной `CHECK_CHROMIUM_PATH`.
Результаты в `checks/results/` и `node_modules/` исключены из Git.
Зависимости проверок изолированы от npm-команд существующего обновлятора.

## Начальное состояние

На базе `ef35708e10db378b03e12df3eb551a10ee374b5f` ежедневный прогон выявляет
отсутствующий `scripts/publication.js`, потерю выбранного срока Т‑Счёта
и отсутствие избранного продукта в выдаче после перезагрузки. Эти проверки
намеренно не помечены как пропущенные или ожидаемо успешные. Первый запуск
на `main` после одобренного объединения PR сообщит о сохраняющихся проблемах.
Исправления сайта, данных и финансовых условий в этот PR не входят.
